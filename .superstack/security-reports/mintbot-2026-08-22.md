# Security audit — mintbot — 2026-08-22

## Executive summary

Full repository, Git-history, dependency, runtime signing, RPC, OpenSea, local-secret, and GitHub-configuration review. No committed wallet key, OpenSea key, RPC credential, seed phrase, or real `.env` file was found in the current tree or Git history. The GitHub repository is private.

Twelve high-confidence findings were verified: one high, seven medium, and four low. Ten were fully remediated during this audit. Two privacy findings remain only in immutable historical commits: a personal author email and old README versions containing a local username/path. The current tree is clean and future commits use a GitHub noreply address, but removing historical metadata requires an explicitly approved history rewrite and force-push.

RustSec initially found two vulnerable locked dependencies. Both were upgraded, and the final audit reports zero known vulnerabilities. Two allowed unmaintained-package warnings remain: `paste` is reachable through Alloy, while `derivative` remains in optional lockfile dependency metadata but is not present in the active Cargo feature graph.

## Scope and architecture

- Rust terminal application; no HTTP server, database, browser automation, or cloud deployment.
- Local EVM private-key signer loaded from process environment or `.env`.
- Outbound HTTPS OpenSea Drops API client.
- Outbound HTTPS JSON-RPC and WSS block/log subscriptions.
- Localhost-only authenticated manual trigger control.
- GitHub Actions, Dependabot, Git configuration, current files, and complete reachable Git history.

## Findings

### [HIGH] MB-SEC-001: Paid OpenSea transactions had no mint-value ceiling

**Confidence:** 9/10
**Phase:** Phase 7 — API Security / Phase 10 — Smart Contract & Transaction Security
**Category:** OWASP A04 / STRIDE T
**Location:** `src/bot.rs:323`, `src/config.rs:218`

**Description:** The OpenSea API supplied the complete payable value, and paid mode accepted any nonzero value that fit the wallet balance. A changed stage price or compromised upstream response could therefore spend substantially more than the operator intended.

**Exploit Scenario:** An upstream response returns the configured contract and plausible calldata but raises `value`. The bot estimates gas, sees sufficient balance, signs, and broadcasts the higher-value transaction because no user-defined mint-price ceiling existed.

**Evidence:** The pre-audit hydration path checked only `require_zero_value`; paid mode had no comparison against a configured maximum.

**Remediation:** **Resolved.** Paid OpenSea setup now requires `max_price_per_nft`, computes a checked total cap for quantity, and aborts before signing when the API value exceeds it. Free mode still requires exactly zero. Regression tests cover lower, equal, and higher values.

**Priority:** P1

### [MEDIUM] MB-SEC-002: Wallet secret file was readable by other local accounts

**Confidence:** 10/10
**Phase:** Phase 2 — Secrets & Credential Audit
**Category:** Infrastructure / STRIDE I
**Location:** `.env`, `src/security.rs:7`

**Description:** The real `.env` existed with mode `0644`, allowing other local OS accounts to read the wallet private key and API/RPC credentials on a shared machine.

**Exploit Scenario:** Another local account reads the world-readable file and uses the private key to transfer the wallet balance or submit unintended transactions.

**Evidence:** Pre-fix `stat` reported `env_mode=644`; the post-fix result is `env_mode=600`.

**Remediation:** **Resolved locally and in code.** The file is now `0600`; startup rejects an overly permissive `.env`; setup documentation requires `chmod 600 .env`.

**Priority:** P1

### [MEDIUM] MB-SEC-003: Locked `time` dependency contained a stack-exhaustion DoS

**Confidence:** 8/10
**Phase:** Phase 3 — Supply Chain Security
**Category:** OWASP A06
**Location:** `Cargo.lock:4325`

**Description:** RustSec advisory `RUSTSEC-2026-0009` affected `time 0.3.45`, which is used to parse OpenSea stage timestamps.

**Exploit Scenario:** A crafted timestamp reaching the vulnerable parser exhausts stack and terminates the bot before a mint.

**Evidence:** Initial `cargo-audit 0.22.2` output identified `time 0.3.45` and required `>=0.3.47`.

**Remediation:** **Resolved.** Lockfile upgraded to `time 0.3.47`; final RustSec audit reports no vulnerability.

**Priority:** P1

### [MEDIUM] MB-SEC-004: Locked `ruint` dependency had incorrect shift/overflow behavior

**Confidence:** 8/10
**Phase:** Phase 3 — Supply Chain Security
**Category:** OWASP A06
**Location:** `Cargo.lock:3618`

**Description:** RustSec advisory `RUSTSEC-2026-0220` affected `ruint 1.17.2`, a core unsigned-integer dependency in the Alloy transaction stack.

**Exploit Scenario:** A reachable shift operation with an oversized amount can produce truncated shifts or incorrect overflow flags, undermining arithmetic assumptions in a transaction path.

**Evidence:** Initial RustSec output required `ruint >=1.20.0`.

**Remediation:** **Resolved.** Lockfile upgraded to `ruint 1.20.0`; final RustSec audit reports no vulnerability.

**Priority:** P1

### [MEDIUM] MB-SEC-005: Production RPC endpoints could use cleartext transport

**Confidence:** 9/10
**Phase:** Phase 5 — Infrastructure Security
**Category:** OWASP A02 / STRIDE I,T
**Location:** `src/rpc.rs:496`

**Description:** Arbitrary `http://` and `ws://` endpoints were accepted, exposing wallet queries, transaction bytes, API-bearing URLs, and trigger data to network interception or modification.

**Exploit Scenario:** An on-path attacker observes or alters cleartext JSON-RPC traffic, feeds false chain state, or interferes with transaction delivery.

**Evidence:** Pre-audit connection helpers parsed URLs without a scheme policy.

**Remediation:** **Resolved.** Non-loopback providers must use `https://`/`wss://`; local Anvil-style loopback endpoints may still use cleartext. Userinfo credentials in URLs are rejected.

**Priority:** P1

### [MEDIUM] MB-SEC-006: Untrusted API/RPC errors could leak data, inject terminal controls, or panic

**Confidence:** 9/10
**Phase:** Phase 7 — API Security / Phase 9 — Injection Audit
**Category:** OWASP A09 / STRIDE I
**Location:** `src/security.rs:29`, `src/opensea.rs:91`, `src/rpc.rs:331`

**Description:** Raw external error strings and OpenSea response bodies reached logs. The old byte-based 512-byte truncation could panic on a UTF-8 boundary. Remote text could also include wallet identifiers, URLs with credentials, newlines, or ANSI control sequences.

**Exploit Scenario:** A compromised or malfunctioning upstream returns a non-ASCII/control-sequence error body. Logging either crashes the process during truncation or prints misleading/sensitive terminal content.

**Evidence:** The old helper called `String::truncate(512)` after checking byte length and printed response bodies verbatim.

**Remediation:** **Resolved.** OpenSea error bodies are omitted, successful JSON responses are streamed with a 1 MiB limit, stage labels are sanitized, and RPC errors retain safe JSON-RPC reasons while redacting URLs, addresses, controls, and excess length.

**Priority:** P1

### [MEDIUM] MB-SEC-007: Concurrent bot processes could select the same wallet nonce

**Confidence:** 9/10
**Phase:** Phase 10 — Smart Contract & Transaction Security
**Category:** STRIDE T / State-machine correctness
**Location:** `src/wallet.rs:59`, `src/bot.rs:1002`

**Description:** Two simultaneously triggered processes using the same wallet could both query the same pending nonce before either broadcast propagated, causing replacement/conflict rather than two independent mints.

**Exploit Scenario:** Two armed mints trigger together. Both fetch nonce `N`, sign different transactions, and broadcast; only one can confirm at that nonce.

**Evidence:** Atomic one-shot state existed only inside one process; no cross-process nonce coordination existed.

**Remediation:** **Resolved for safe nonce modes.** An owner-only per-wallet file lock serializes final nonce refresh, signing, and first broadcast for `just_before_trigger` and `refresh_each_block`. Expert `preloaded` mode remains explicitly exclusive-wallet-only.

**Priority:** P1

### [MEDIUM] MB-SEC-008: Contract validation accepted inconsistent RPC bytecode

**Confidence:** 9/10
**Phase:** Phase 7 — API Security / Phase 10 — Transaction Security
**Category:** STRIDE T
**Location:** `src/rpc.rs:158`

**Description:** Startup rejected a missing contract only when every provider returned empty bytecode. A faulty/malicious provider could disagree with healthy providers and the bot would still arm.

**Exploit Scenario:** One provider reports bytecode while another reports no code or different code. The bot trusts the mixed set and proceeds using inconsistent chain state.

**Evidence:** The former condition was `codes.iter().all(|code| code.is_empty())` with no equality check.

**Remediation:** **Resolved.** Any deployed/not-deployed disagreement or bytecode-hash mismatch now fails closed.

**Priority:** P1

### [LOW] MB-SEC-009: README exposed a local username and absolute workspace path

**Confidence:** 10/10
**Phase:** Phase 11 — Data Privacy
**Category:** STRIDE I
**Location:** `README.md`

**Description:** Two committed Markdown links contained an absolute `/Users/.../workspace/mintbot` path, revealing local account/workstation information on GitHub.

**Exploit Scenario:** A repository reader correlates the local account name with other public or leaked metadata for targeted phishing or host reconnaissance.

**Evidence:** Current-history search found two `/Users/` links in README.

**Remediation:** **Partially resolved.** Both links are repository-relative in the current tree, and a current-tree rescan finds no local absolute path. Old commits retain the prior path until the same approved history rewrite required by MB-SEC-011.

**Priority:** P2

### [LOW] MB-SEC-010: Personal mint configs were commit-prone and saved too broadly

**Confidence:** 9/10
**Phase:** Phase 2 — Secrets / Phase 11 — Data Privacy
**Category:** STRIDE I
**Location:** `.gitignore:13`, `src/config.rs:176`

**Description:** Generated JSON configs defaulted to normal process permissions and were not ignored. They can contain wallet-specific proofs, collection targeting, timing, pricing, and execution strategy.

**Exploit Scenario:** A user runs setup, later stages the generated config with a broad Git add, and exposes wallet-linked mint strategy or proof data.

**Evidence:** Only `.env`, build output, trigger files, and `.DS_Store` were ignored; `fs::write` used default permissions.

**Remediation:** **Resolved.** Personal `configs/*.json` files are ignored except the placeholder example, and saved configs are forced to mode `0600` on Unix.

**Priority:** P2

### [LOW] MB-SEC-011: Existing Git history exposes a personal author email

**Confidence:** 10/10
**Phase:** Phase 2 — Secrets / Phase 11 — Data Privacy
**Category:** STRIDE I
**Location:** Git commit metadata across existing branches

**Description:** Existing commits use a non-noreply personal/organizational email. Repository privacy limits readership, but every collaborator and exported clone can inspect it.

**Exploit Scenario:** A repository reader extracts author metadata and correlates the address with identity, employer/education, password-reset targets, or phishing campaigns.

**Evidence:** `git log --all --format='%ae'` reports a non-`users.noreply.github.com` domain.

**Remediation:** **Partially resolved.** Repository-local Git config now uses the account's GitHub noreply address for future commits. Historical removal requires rewriting every affected commit and force-pushing all affected branches; this was not performed without explicit approval.

**Priority:** P1 for the user's stated privacy goal

### [LOW] MB-SEC-012: GitHub dependency vulnerability controls were disabled

**Confidence:** 10/10
**Phase:** Phase 3 — Supply Chain / Phase 5 — Infrastructure
**Category:** OWASP A06
**Location:** GitHub repository settings, `.github/dependabot.yml`, `.github/workflows/security.yml`

**Description:** Dependency graph vulnerability alerts, security updates, and CI advisory checks were absent, allowing newly disclosed vulnerable crates to remain unnoticed.

**Exploit Scenario:** A new advisory affects a locked dependency after deployment; no repository control notifies the owner or blocks future changes.

**Evidence:** GitHub API initially returned vulnerability alerts disabled; no workflows or Dependabot configuration existed.

**Remediation:** **Resolved where supported.** GitHub vulnerability alerts and automated security fixes are enabled; weekly Cargo/Actions updates and pinned, read-only CI checks were added. GitHub secret scanning/push protection is unavailable for this private repository's current plan, so ignore rules, history scans, and CI hygiene remain the fallback.

**Priority:** P2

## Verification

- Current tree and reachable Git history: no committed real `.env`, private key, OpenSea API key, RPC credential, PEM key, or seed phrase.
- Current tree: no local absolute path. Historical commits retain the remediated README path and author email until an approved rewrite.
- `.env`: ignored, absent from history, mode `0600`.
- `cargo test --locked --all-targets`: 30 passed, 0 failed after remediation.
- `cargo clippy --locked --all-targets --all-features -- -D warnings`: passed.
- `cargo fmt --all --check`: passed.
- `cargo-audit 0.22.2`: zero known vulnerabilities after upgrades; two allowed unmaintained transitive warnings (`derivative`, `paste`).
- Gitleaks 8.30.1: current tree and all nine reachable commits scanned; no leaks found.
- GitHub: private repository; vulnerability alerts enabled; automated security fixes enabled; default Actions token permission is read; immutable checkout action pinned.

## Residual risk and roadmap

1. **P1, 30–60 minutes, destructive approval required:** Rewrite affected commit metadata to the GitHub noreply address, remove old local-path content from reachable history, force-push all affected branches, and invalidate old clones/PR references.
2. **P2, 15 minutes after merge:** Consider protecting `main` with required pull requests and the `Security checks` status. This changes the solo-owner push workflow and was not enabled automatically.
3. **P2, ongoing:** Monitor and remove the transitive unmaintained `derivative` and `paste` crates when Alloy releases a dependency path without them.
4. **P2, optional assurance:** Add property/model checks for the one-shot submission and cross-process nonce invariants; tests now cover the primary guards, but this is transaction-state-machine logic.
5. Continue using a dedicated, minimally funded mint wallet; a plaintext hot key in a local file remains inherently higher risk than a hardware/KMS signer.
